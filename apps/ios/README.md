# Poravia for iOS and iPadOS

The native SwiftUI application. App target `Poravia`, bundle identifier
`dev.peterdsp.poravia`, deployment target iOS 17.0, Swift 6 language mode,
marketing version `1.0.0`.

## Known blocker: the shared core terminates the app on a fresh install

A Release or Debug build that uses the real core **crashes at launch on a
device with no packs installed**. Reproduced on iPhone 15, iOS 27.0:

```
$ xcrun simctl launch --console-pty <udid> dev.peterdsp.poravia
Exception doesn't match @Throws-specified class list and thus isn't propagated
from Kotlin to Objective-C/Swift as NSError.
It is considered unexpected and unhandled instead. Program will be terminated.
Uncaught Kotlin exception: dev.peterdsp.poravia.core.PoraviaException:
  No offline data is installed yet.
    at kfun:dev.peterdsp.poravia.core.PoraviaCoreImpl.$indexCOROUTINE$16…
    at kfun:dev.peterdsp.poravia.core.PoraviaCoreImpl.PoraviaCoreImpl$meta$2…
```

This is a core-side defect and cannot be fixed from Swift: an exception that is
not in a Kotlin function's `@Throws` list is never converted to `NSError`, so
there is nothing for the adapter to catch. The process is killed by the Kotlin
runtime before any Swift code runs.

**The fix belongs in `shared/core`**: every exported suspend function that can
raise `PoraviaException` needs it declared, for example

```kotlin
@Throws(PoraviaException::class, CancellationException::class)
override suspend fun meta(): Meta = …
```

applied to `meta`, `coverage`, `sources`, `searchPlaces`, `searchJourneys`,
`journeyDetail`, `operatorDetail`, `stopDetail`, `savedTrips`, `saveTrip`,
`removeSavedTrip`, `favorites`, `toggleFavorite`, `recentSearches`,
`offlineCatalog`, `installedPacks`, `removePack` and
`rollbackToPreviousRelease`. `CoreErrorTranslation` already reads
`PoraviaException.code` and `.field` and maps them onto the five contract
errors, so no Swift change is needed once the exception propagates.

Until then, every runtime screenshot in `artifacts/screenshots/` was captured
with `-PoraviaUseFixture`, which exercises the whole interface without the
core. The Release build still links the core and passes every artefact check;
what is unproven is the core's **runtime** behaviour on this platform.

## The project is generated, never hand-edited

`Poravia.xcodeproj` is not checked in. It is generated by XcodeGen from
`project.yml` (and `project-core.yml` when the shared core is present), so the
spec and what actually builds cannot drift apart.

```bash
bash scripts/ios-bootstrap.sh
```

That one command regenerates everything derived from a source of truth and then
generates the project:

| Source of truth | Generated |
|---|---|
| `brand.json` | `Poravia/Generated/Brand.swift` |
| `design/tokens/poravia.tokens.json` | `Poravia/Generated/Theme.swift`, brand colour sets |
| `design/logo/poravia-mark.svg` | app icon (light, dark, tinted), brand mark, wordmark |
| `Poravia/Resources/strings.source.json` | `Localizable.xcstrings`, `Poravia/Generated/L10n.swift` |
| `shared/core/build/XCFramework/` | `Frameworks/PoraviaCore.xcframework` |

Nothing in the generated files is edited by hand. Change the source and re-run.

Variants:

```bash
PORAVIA_CORE_VARIANT=debug bash scripts/ios-bootstrap.sh   # link the debug core
PORAVIA_CORE_VARIANT=none  bash scripts/ios-bootstrap.sh   # build with no core
```

## The shared core is the only source of domain logic

Every question about timetables goes through one Swift protocol,
`PoraviaCoreClient`, which mirrors the exported Kotlin `PoraviaCore` API one for
one. Below it:

- `PoraviaCoreAdapter` — the only production conformance, a thin adapter over the
  `PoraviaCore` XCFramework. `CoreMapping` converts each Kotlin value into its
  Swift mirror field by field.
- `UnavailableCoreClient` — used when the framework is not linked. It reports the
  missing core as its own state rather than inventing results.
- `FixtureCoreClient` — Debug only, backed by the invented Aloria dataset, for
  previews, tests and the simulator walkthrough.

Contract decoding, search coordination, sorting, service-date and
`Europe/Athens` rules, midnight crossing, freshness thresholds, favourites,
saved trips and the whole offline-pack lifecycle (download, resume, SHA-256
verification, atomic install, rollback) all live in the core. **No Swift code
opens an offline pack or assumes anything about a pack's contents.**

`ServiceDate` deliberately has no arithmetic: `currentServiceDate(now:)` and
`shiftServiceDate(_:byDays:)` are on the protocol, so the core decides.

### The fixture cannot reach a Release build

`FixtureCoreClient`, `FixtureScenario` and `AloriaFixture` are all inside
`#if DEBUG`, so a Release build cannot name them. That is the compile-time
guard. `ReleaseGuardTests` asserts the runtime consequence and
`scripts/ios-verify-release.sh` proves no fixture symbol is defined in the
archived binary.

## Running on fixture data

A Debug build can be launched on the fixture, so every state is reachable on a
simulator with no server:

```bash
xcrun simctl launch <udid> dev.peterdsp.poravia \
  -PoraviaUseFixture -PoraviaFixtureScenario corruptDownload -PoraviaResetState
```

Scenarios: `normal`, `offline`, `serverError`, `emptyResults`, `notCovered`,
`partialCoverage`, `releaseMismatch`, `corruptDownload`, `interruptedDownload`,
`insufficientStorage`, `staleRelease`, `coreUnavailable`, `servedFromCache`.

A Release build ignores `-PoraviaUseFixture` entirely, because it has no fixture
to select.

## Layout comes from the container, never from the device

`WindowGeometryReader` measures the actual container once at the root and
publishes a `WindowGeometry` and a `LayoutMode` into the environment. Every
decision reads the real usable width, the safe areas, any reserved regions, the
keyboard and the Dynamic Type size. There is no `UIScreen`, no device check and
no assumption that the scene fills the display, so Split View, Slide Over, Stage
Manager and any resized window are all handled by the same code path.

### iPhone Duo and reserved regions

The installed toolchain is Xcode 27.0 with the iOS 27.0 SDK, which exposes **no
public API for a foldable's reserved or occluded region**:

- `SwiftUI.ReservedRegion` and
  `GeometryProxy.reservedRegions(kind:options:layoutDirectionBehavior:)` exist
  as linker symbols in `SwiftUICore.tbd` but are absent from the public
  `SwiftUI.swiftinterface`. A typecheck against `iphonesimulator27.0` fails with
  `value of type 'GeometryProxy' has no member 'reservedRegions'`.
- `UIViewLayoutRegion` (iOS 26+) is about display-corner adaptation only.
- No UIKit header in this SDK mentions a hinge, a posture or an occluded area.

So `SystemReservedRegionSource` reports nothing rather than guessing. A posture
is never inferred from an aspect ratio, a screen size or a device model.
`LayoutResolver` therefore runs on pure geometry, which is correct on every
device including a foldable, and stays correct the moment regions do arrive:
the single `regions(...)` method is the only thing that has to change.

## Tests

```bash
xcodebuild -project apps/ios/Poravia.xcodeproj -scheme Poravia \
  -destination 'platform=iOS Simulator,name=iPhone 15' \
  -only-testing:PoraviaTests test
```

- `LocalisationTests` — every key in `el`, `en` and `sq`, matching format
  specifiers, a translator comment on each key, no orphan keys, no legacy
  product name in any string, and the three languages genuinely differing.
- `CoreBoundaryTests` — the Release guard, service dates, contract instants,
  unknown enumeration handling, and one distinct presentation per error.
- `LayoutTests` — the layout resolver against explicit geometry fixtures,
  including asymmetric split windows, plus deep-link validation and filters.
- `WalletAndReminderTests` — the wallet's type, size, protection, backup
  exclusion and real-deletion rules, and reminder identity and payload.
- `FixtureFlowTests` — every flow and failure scenario end to end.

## Release verification

```bash
xcodebuild -project apps/ios/Poravia.xcodeproj -scheme Poravia \
  -configuration Release -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /tmp/poravia-release build
bash scripts/ios-verify-release.sh /tmp/poravia-release/Build/Products/Release-iphonesimulator/Poravia.app
```

It checks the built artefact, not the source: core symbols present, no fixture
symbol defined, no legacy name anywhere, bundle identity, usage descriptions,
the associated-domain entitlement, the privacy manifest, the three
localisations, the icon's three appearances, and the absence of any known
analytics SDK.

## Signing and export

This machine has **no distribution signing identity and no provisioning
profile**, so no installable beta can be produced here. What exists:

```
$ security find-identity -v -p codesigning
  Apple Development: PETROS DHESPOLLARI (29VHPQP8K8)   (x2)
$ ls ~/Library/MobileDevice/Provisioning\ Profiles/
  (empty)
```

Development identities cannot sign a distribution build, and
`xcodebuild -exportArchive` additionally fails with
`Failed to Use Accounts` because the keychain holds no App Store Connect
credentials. **A simulator build is not an installable iPhone beta.**

To produce one, three things are needed, none of which can be invented:

1. An Apple Developer Program team, and its Team ID.
2. A distribution certificate plus a matching provisioning profile for
   `dev.peterdsp.poravia` (or an App Store Connect API key for automatic
   signing).
3. An App Store Connect account added in Xcode's Accounts settings.

Then:

```bash
xcodebuild -project apps/ios/Poravia.xcodeproj -scheme Poravia \
  -configuration Release -destination 'generic/platform=iOS' \
  -archivePath build/Poravia.xcarchive \
  DEVELOPMENT_TEAM=<TEAM_ID> CODE_SIGN_STYLE=Automatic archive

xcodebuild -exportArchive -archivePath build/Poravia.xcarchive \
  -exportPath build/export -exportOptionsPlist ExportOptions.plist
```

with `ExportOptions.plist`:

```xml
<dict>
  <key>method</key>              <string>app-store-connect</string>
  <key>destination</key>         <string>export</string>
  <key>teamID</key>              <string><!-- TEAM_ID --></string>
  <key>uploadSymbols</key>       <true/>
  <key>signingStyle</key>        <string>automatic</string>
  <key>manageAppVersionAndBuildNumber</key> <false/>
</dict>
```

The unsigned archive at `/tmp/Poravia.xcarchive` proves the Release
configuration compiles, links the shared core and passes every bundle check;
only the signature is missing.
