# Signing the Poravia Android application

**Status for 1.0.0 beta: there is no release signing identity, and none was
invented.**

A signing key is the application's identity. Once a build signed with a key
reaches a device, only builds signed with that same key can ever update it. A
key generated by a build script, committed to a repository, or created by an
automated agent to make a command succeed is not a production signing identity,
and presenting one as if it were would be worse than shipping unsigned: it would
quietly commit the product to a key nobody controls.

So the release outputs in this repository are **unsigned on purpose**, and they
are labelled as such. What follows is exactly what a human with the authority to
hold the key has to do.

## What exists today

| Artifact | Signing | Installable | Distributable |
|---|---|---|---|
| `poravia-debug.apk` | Android debug key | yes | no |
| `poravia-releaseSmoke.apk` | Android debug key, minified and shrunk | yes | no |
| `poravia-release-unsigned.apk` | none | no | no |
| `poravia-release.aab` | none | no | no |

`releaseSmoke` exists because the release configuration is the one that
matters: it is minified, resource-shrunk and obfuscated, and a bug that only
appears under R8 is exactly the bug that reaches people. It is the release build
with the ordinary Android debug key attached so it can actually be installed and
exercised on an emulator, and its version name carries `-releasesmoke` so it can
never be mistaken for a distributable artifact.

## Creating the release identity

Do this once, on a machine the key owner controls, and never in CI.

```sh
keytool -genkeypair -v \
  -keystore poravia-release.jks \
  -storetype PKCS12 \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -alias poravia \
  -dname "CN=Poravia, O=Poravia, C=GR"
```

Back the keystore up somewhere the owner controls and that survives losing the
machine. Losing it means the application can never be updated again under the
same package name.

## Wiring it into the build

Create `keystore.properties` at the repository root. It is gitignored and must
stay that way.

```properties
storeFile=poravia-release.jks
storePassword=…
keyAlias=poravia
keyPassword=…
```

`apps/android/build.gradle.kts` picks the file up when it exists and signs the
`release` build type with it. When it does not exist, the release build is left
unsigned, deliberately, with no fallback key.

Then:

```sh
export JAVA_HOME=/opt/homebrew/opt/openjdk@21
export PATH="$JAVA_HOME/bin:$PATH"
./gradlew :apps:android:bundleRelease
```

## Play App Signing

Google Play re-signs uploads with a key Google holds. The key above becomes the
*upload* key. That changes nothing here except which certificate fingerprint
goes into Digital Asset Links: it must be the **app signing** certificate Play
shows under Release, Setup, App signing, not the upload certificate.

## Digital Asset Links, and why `autoVerify` is off

`AndroidManifest.xml` declares the `https://poravia.peterdsp.dev/...` intent
filter **without** `android:autoVerify="true"`. That is a deliberate choice and
not an oversight.

Android verifies an App Link by fetching
`https://poravia.peterdsp.dev/.well-known/assetlinks.json` and matching the
SHA-256 fingerprint of the signing certificate. That file does not exist yet,
because there is no signing certificate yet. Declaring `autoVerify` now would
produce a link that fails verification on every install, and a failed
verification is worse than no declaration: the link stops opening the
application at all on Android 12 and later, silently.

Without `autoVerify` the https links still work through the ordinary chooser,
and the `poravia://` scheme works unconditionally and needs no domain
verification at all.

To turn verification on, once a signing identity exists:

1. Get the fingerprint:

   ```sh
   keytool -list -v -keystore poravia-release.jks -alias poravia \
     | grep 'SHA256:'
   ```

   With Play App Signing, take the fingerprint from the Play Console instead.

2. Publish this at `https://poravia.peterdsp.dev/.well-known/assetlinks.json`,
   served as `application/json` over https with no redirect:

   ```json
   [{
     "relation": ["delegate_permission/common.handle_all_urls"],
     "target": {
       "namespace": "android_app",
       "package_name": "dev.peterdsp.poravia",
       "sha256_cert_fingerprints": ["<SHA-256 of the app signing certificate>"]
     }
   }]
   ```

3. Add `android:autoVerify="true"` to the https intent filter in
   `apps/android/src/main/AndroidManifest.xml`.

4. Verify on a device:

   ```sh
   adb shell pm verify-app-links --re-verify dev.peterdsp.poravia
   adb shell pm get-app-links dev.peterdsp.poravia
   ```

   The domain must report `verified`.

Until all four steps are done, leave `autoVerify` off.

## The mapping file

`release` and `releaseSmoke` are minified, so a stack trace from either needs
deobfuscating. The mapping file is written to:

```
apps/android/build/outputs/mapping/release/mapping.txt
```

Upload it with the bundle. It is build output and is not committed.

## Native debug symbols

`ndk { debugSymbolLevel = "SYMBOL_TABLE" }` is set on the release build type, so
the bundle carries symbols for the native libraries the SQLite driver brings in.
Play uses them to symbolicate native crashes.
