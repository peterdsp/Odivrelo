# Data Recovery Inventory

Prepared 3 October 2026 from the local checkout at `/Users/peterdsp/git/Odivrelo`.
Machine-readable companion: `docs/beta/data-recovery-inventory.json`.

This document records where the earlier KTEL acquisition work went, what was
recovered, and the exact remaining locations and owner actions. It is based on
direct inspection of the local artifacts, databases and git history, not on a
re-run of the July analysis.

## Headline answer: where were the 19,872 raw records?

They were never stored as individual rows in this repository or its artifacts.

- `19,872` is the sum of the integer `stops` field across the 26 `ktel-`
  TicketWeb tenants in the `ticketwebTenants` array of
  `server/ktel-staging/pkg/ktel/operators.json`.
- The companion sums verify exactly:
  - 26 `ktel-` tenants: stopGroups `5,378`, stops `19,872`, webActiveStops `511`.
  - all 28 tenants (adding `amorgos-bus` and `hypertours-trikala`): `5,420`,
    `19,957`, `519`.
- Those are observed aggregate counts from the July 2026 directory pass. They
  are not persisted stop records. The same file carries no per-stop bodies.
- The TicketWeb source is configured `retentionMode: metadata_only`,
  `retentionDays: 0`, `rightsStatus: permission_pending`. Under that policy the
  raw bodies were deliberately not retained after counting.

So the number is real, the rows behind it are not present locally. The only
place they could still survive is the Raspberry Pi (see Remaining locations).

## Why the gap between July and today

Classification: records not retained.

The July TicketWeb pass counted stops under a metadata only, zero day retention
policy with pending reuse rights, so the individual bodies were never normalized
into `ingest.db`. The current releases ship the labelled Aloria demo because no
real source passed the data gate for 1.0.0: TicketWeb reuse is not granted, and
NAP 2020 passed the licence gate but failed the freshness and completeness gate.
The demo was generated by the release path; there is no evidence of a prior real
import that was lost or overwritten.

Ruled out by evidence:
- lost during migration: no prior real import appears in git history or local
  artifacts.
- overwritten by demo generation: no prior real rows were found that a demo run
  could have replaced.

Still unresolved (needs Pi access to settle):
- held remotely: the Pi may hold a transient or backup copy of raw TicketWeb
  rows. Unverifiable until access is restored.

## Raspberry Pi investigation (3 October 2026): question closed

Pi access was restored and the known locations were inspected read-only. The
`sqlite3` CLI is not installed on the Pi, so the Pi's own venv Python
(`~/syrmos-api/.venv/bin/python`) with the `sqlite3` module was used.

Finding: the Pi contains no KTEL coach data of any kind.

- The documented `~/syrmos-api/db/ktel.db` and `ktel-public.db` do not exist. A
  search of `/mnt/media` and the home tree (depth 5) found no `ktel*.db`,
  `ktel-public*`, `ingest.db` or `public.db` anywhere.
- `~/syrmos-api/db/syrmos.db` has 28 tables, all rail and urban transit
  (`stations`, `lines`, `line_stations`, `scheduled_trips`,
  `scheduled_trip_stops`, `frequency_bands`, `stasy_status`, `rail_news`,
  `fare_products`, ...). There are zero `ktel_*` tables.
  `~/syrmos-api/data/syrmos.db` has 11 tables, also zero `ktel_*`.
- `~/syrmos-api/out/ktel/` is rail output despite the name (Metro and bus line
  schedules such as `M3_AIR`, `DK1`, `X3`; `oasa-airport-buses.json`).
  `~/syrmos-api/reference/` is STASY rail PDFs.
- No log under `~/syrmos-api` ever fetched `ktelbus.com`, `ktelbus.gr`,
  `ticketweb` or `data.nap.gov.gr`.
- The `~/hodomap` checkout (the original Odivrelo name) holds only
  `data/operators/registry.json` and README stubs: no database, no raw stops,
  the same metadata-only state as this local checkout.

The Pi runs the separate Syrmos rail product. Its databases were deliberately
not snapshotted or copied: they contain no KTEL rows, and this engagement must
not touch Syrmos or copy unrelated data.

Conclusion: the 19,872 individual TicketWeb rows were never retained anywhere,
locally or on the Pi. They existed only as aggregate counts. This question is
permanently closed. The only real, permitted dataset available is the historical
NAP 2020 workbook.

## NAP 2020 candidate import (done, 3 October 2026)

With no Pi data to recover, the NAP 2020 workbook is the only real source. It is
now parsed into the import contract and loaded as candidates:

- Parser: `server/ktel-staging/odivrelo_ktel/nap_parser.py` (both workbook
  layouts, Greek day-prose calendars, overnight handling, ODbL lineage, original
  text retained). Tests: `server/ktel-staging/tests/test_nap_parser.py`.
- CLI: `scripts/ktel_pipeline.py normalize-nap-xlsx <workbook>` (needs
  `server/ktel-staging/requirements.txt`, openpyxl).
- Result: 42 of 62 operators, 1,340 candidate trips, 263 city stops (all
  coordinate-missing, candidate), 260 lines, 228 calendars. Zero published.
  Full reconciliation: `docs/beta/nap-reconciliation.json` and
  `OPERATOR-COVERAGE-LEDGER.md`.

It is deliberately not published: 2020 and city-level data fails the freshness
and boarding-evidence gates. It stays candidate until a current authoritative
source confirms service dates and physical boarding points. Directory-only
operators remain listed with the official handoff and an explicit
lack-of-timetable state.
